As-Is domain model

youtube-mcp が今持っているドメインモデル

現行コードだけから読み取れる概念・型・判断の置き場所を図に起こしたもの。設計ドキュメント（docs/）の記述ではなく、internal/ 配下の実装から逆算している。作り直しの起点として、何が型になっていて、何がなっていないかを境界線として示す。

型の地図 — 実体として存在する概念

この題材の中心語彙は「再生リスト」「動画」「エントリ」「視聴可否」の四つ。コード上で型を与えられているのはそのうち三つで、動画そのものは型を持たない。

判断がどこに置かれているか

functional core / imperative shell の分離自体は効いていて、純粋関数は organizer に六つ集まっている。ただし「ドメインの決まりごと」はその六つの外にも散っている。下図の破線チップが、純粋関数として取り出されずコードに直書きされている判断。

Figure 3

検出と実行のあいだに何も無い

「整頓」というこのサーバの中心行為は、検出と実行という二回の独立した MCP 呼び出しに分かれている。その二回をつなぐ計画そのものは、どこにも型として存在しない。

Figure 4

move の途中に生まれる、型の無い状態

移動は insert → delete の二段で行われる。その間に「両方の再生リストに存在する」という中間状態が必然的に生まれ、delete が失敗するとそこで固定される。この状態はコード中で transient duplicate と呼ばれているが、文字列メッセージの中にしか存在しない。

Seams

作り直すときに切れ目になりそうな箇所

いずれも「今の実装が壊れている」という話ではなく、モデルとして言語化されていないものの一覧。

同一性

二種類の ID がどちらも string。削除の単位は PlaylistItemID、同一性の単位は VideoID。区別はコメントでしか保証されていない。

層の兼務

1 つの構造体が 3 役を負っている。youtube.Playlist は API 応答の形・ドメイン概念・MCP 出力スキーマを同時に担う。片方を変えると他方が動く。

集約境界

再生リストと、その中身の関係が型に無い。ItemCount と実際の items は別経路で取得され、DeletePlaylist は全件列挙から線形探索して件数を見る。

中核概念

「整頓」を表す型が無い。検出結果と実行要求をつなぐのは平坦な ID 配列だけ。計画・承認・適用という段階が概念として存在しない。

安全性

dryRun が引数として全層を貫通している。「計画を作る」と「計画を適用する」の分離で表せるものが、bool フラグとして入力にも結果にも現れている。

不変条件

規則の置き場所が層ごとにばらばら。空チェックは organizer、視聴可否は youtube、宛先の排他は殻の if、安全既定は MCP 層。

失敗の表現

エラーが string に潰れる。「挿入失敗」と「二重登録のまま残った」は回復手順がまるで違うのに、呼び出し側からは同じ形で届く。

ポート

Client が 8 メソッドの単一インタフェース。読取・作成・削除が同居し、ユースケースが増えるたびに肥大する。分割の軸がまだ引かれていない。
